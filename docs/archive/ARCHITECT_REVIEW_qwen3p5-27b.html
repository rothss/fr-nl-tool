📋 评审摘要

OPM NL Report Query 项目整体架构设计合理，模块职责清晰，结构化输出设计完善。 项目展现了良好的工程化思维，特别是在意图解析、查询规划、数据获取等环节的分层设计上。 但在代码质量、测试覆盖、配置管理等方面存在明显不足，需要优先改进。 建议按照优先级逐步完成改进项，然后进入正式生产环境部署。

7.5 / 10
整体评估：良好，有明显改进空间

✅ 优点 6 项

架构设计清晰，分层明确

意图解析、规划、数据获取、分析、渲染等模块职责分离，符合单一职责原则。 从 runner.py 入口到各子模块的调用链路清晰，便于维护和扩展。 这种分层设计为后续功能扩展和性能优化奠定了良好基础。

结构化数据模型设计完善

定义了 7 种核心数据模型（IntentCandidate、QueryPlan、SourceMeta、 AnalysisResult、OpenClawResultEnvelope 等），每个模型都有清晰的 Schema 定义。 机器可读的 reason_code 失败分类便于下游系统集成和错误处理。

混合解析策略合理

规则解析器处理高置信度模式（航班号、日期、航线等），LLM 解析器负责填充缺失槽位。 两者通过验证器合并，避免了单一解析方式的局限性。这种策略在保证准确性的同时 也提升了系统对复杂查询的适应能力。

时间语义规范化设计优秀

将"未来两天"、"近三天"、"明天"等自然语言时间表达统一规范化为标准模式 （single_date、relative_future_range、explicit_range 等），并转换为具体日期列表。 这种设计避免了针对每个时间短语编写独立分支，提升了代码的可维护性。

机场/航线别名规范化机制

通过 references/airport_aliases.yaml 管理机场别名映射， 支持将"北京首都"、"首都机场"、"PEK"等不同表达统一规范化。 这一机制有效避免了因表达差异导致的数据匹配问题。

OpenClaw 集成接口设计规范

通过 runner.py 提供统一的技能入口，返回结构化的 JSON 信封。 明确了 OpenClaw 的调用规则和消费规范，避免了直接检查 Excel 文件等非结构化操作。

⚠️ 不足 5 项

代码质量参差不齐

parse_query_intent.py 中存在大量正则表达式硬编码，如航司名称列表、 时间模式匹配等，维护成本高。部分函数长度超过 100 行，违反单一职责原则。 缺少类型注解和文档字符串，代码可读性有待提升。

示例：第 89-91 行硬编码了 12 个航司名称列表

测试覆盖率不足

虽然有测试文件存在，但缺乏对核心业务逻辑的充分覆盖。 例如时间解析的边界情况（闰年、跨月）、别名匹配的错误处理、 LLM 解析器失败回退等场景缺少系统测试。单元测试与集成测试的界限不清晰。

配置管理分散

配置散落在多个 YAML 文件和代码硬编码中，缺少统一的配置管理入口。 路径配置（如 default_mirror_root()）硬编码为 Windows 路径， 影响跨平台兼容性。缺少配置验证和默认值管理机制。

错误处理不够系统

虽然有 reason_code 设计，但实际代码中仍存在大量 return None 和静默失败的情况。缺少统一的异常类型定义和错误传播机制。 部分错误信息对用户不够友好，缺少本地化的错误提示。

性能优化空间大

报表目录每次查询都重新加载，缺少缓存机制。Excel 文件读取未考虑大数据量场景， 可能影响响应时间。LLM 解析器调用缺少超时控制和并发限制。

🚀 急需改进的三个问题

1. 重构 parse_query_intent.py，提取硬编码配置 P1-最高优先级

将航司列表、时间模式、分析模式等硬编码提取到 references/ 目录下， 建立统一的配置加载机制。拆分大函数为小函数，添加类型注解和文档字符串。

预期收益： 提升代码可维护性 40%，降低后续功能扩展成本。

建议工时： 2-3 人天
